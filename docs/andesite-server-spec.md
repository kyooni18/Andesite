## 1. Scope, guarantees, and limits

AndesiteServer manages one or more vaults of ordinary UTF-8 Markdown and opaque attachments. Files are canonical for their **current visible contents and paths**. SQLite holds durable identity, revisions, operation and sync metadata as well as rebuildable indexes. Private immutable content objects retain exact bytes needed for recovery, history, conflicts and protocol delivery; they are operational history, not the authoritative current document. A SQLite rebuild must never write or delete vault files.

Ordinary external applications may create, edit, replace, rename, move and delete files at any time while the server runs; no Andesite lock, integration or particular save method is required. The per-vault coordinator serializes Andesite's own operations and observations only. One server process owns a state directory and vault; a process-lifetime OS lock prevents another Andesite instance using that state directory, not external editors. Operators must not configure the same vault root under different state directories or server instances, which this lock cannot detect. Clustered writers and network filesystems are unsupported.

**Durability and concurrency boundaries:** (1) An accepted server operation has a committed, durable outcome and, for content-bearing operations, a retained immutable copy of the submitted bytes; its history is retained for the policy in §10.6 and longer when pinned. (2) An external state is captured only once its bytes and identifying metadata are durably recorded; such a captured revision has the same retention guarantees. (3) For a concurrent external write, the server checks and captures detectable changes, preserves available versions and never knowingly replaces a conflicting observed version. These checks are best effort: ordinary filesystem replacement is not a compare-and-swap on file content. (4) An intermediate external write never observed or durably captured cannot be preserved or reconstructed by the server. Editing applications can themselves overwrite their own previous writes.

An external write may occur after the last check and before rename, or through an already-open file descriptor to a displaced inode. Atomic rename, notifications, hashing, stat checks, preimages and post-write validation do not eliminate those races; some writes can be lost without observation. A detected ambiguity becomes an explicit conflict or pending recovery, never an automatic winner. Backups and the journal protect retained versions within their stated retention and storage-durability assumptions; they do not turn the filesystem and SQLite into one atomic transaction. `applied` means the requested filesystem effect was observed at verification and durably published, not that it remains the current file after another writer acts. A client retains its local edit until a durable outcome is recorded locally.

## 3. Components and concurrency

Dependency arrows point inward: `Server -> Protocol, Core`; `Core -> Storage, Markdown, Index, Sync`; implementation modules depend on shared domain value types, not Hummingbird. To avoid circular coupling, `AndesiteDomain` owns IDs, revisions, errors and interfaces; `AndesiteProtocol` owns wire DTOs and has no storage/framework dependency. `Sync` orchestrates domain ports; Storage and Index implement ports and do not call Sync. Markdown returns extracted facts; Index resolves them. Modules may initially be SwiftPM targets within one package, not separate deployable services.

A per-vault actor serializes **server-originated** mutations, recovery, external observation and event allocation. It does not make a cross-filesystem transaction atomic and must not hold mutable state across an `await` without a reentrancy-safe operation token. Disk, hashing, parsing and SQLite operations run on bounded blocking executors, never on NIO event loops. Parsing can run concurrently on immutable snapshots; index commit verifies the indexed revision is still current. SQLite has one serialized writer and a small bounded pool of read-only connections, each confined to its executor. Use structured task cancellation, bounded request bodies, bounded queues and backpressure. A crash or cancellation after durable prepare is resolved through the journal, not by an in-memory defer.

## 4. Vault layout, identity and filesystem security

Example:

```
/vaults/research/Notes/Example.md       # ordinary files, no ID injected
/vaults/research/Images/chart.png
/state/server.sqlite3                  # outside every vault
/state/objects/ab/cd...                # immutable blobs named by SHA-256
/state/staging/<operation-id>/         # private, durable operation inputs
/state/locks/server.lock               # Andesite process ownership only
```

Each vault, document, attachment and operation has a random UUID. Vault IDs and entry IDs reside in the SQLite operational catalog; `entries` maps an ID to a normalized relative path. Markdown and binary files are equal entry types; only Markdown is parsed. No per-file sidecars are created. Managed moves preserve ID. External moves are associated only if the watcher provides a credible paired rename **and** a scan validates it, or if a disappeared entry and new entry are uniquely matched by a retained stable filesystem identity and compatible evidence. An inode is a hint, can be reused, and atomic-save editors often replace it. Identical hashes or names alone are not proof. Ambiguous/unverified cases become deletion plus creation with new ID, even if bytes match; surface candidate matches for an explicit, audited administrator/client relink. Hard links are rejected/ignored with a diagnostic because one inode with multiple paths undermines identity and safe replacement. Offline sync clients can retain old IDs only if catalog and relevant history are retained.

The state directory plus a consistent vault snapshot is the portable **full backup**: it includes SQLite, immutable blobs, cursor keys and vault files at a consistent point. For a guaranteed coherent backup, an operator may temporarily stop external writers, drain/recover pending work in Andesite, then stop Andesite and capture both vault and state before resuming them; alternatively use a storage-level atomic consistency-group snapshot covering all vault, SQLite/WAL and blob volumes, with SQLite's documented snapshot/backup requirements. This is a backup procedure, not a condition on ordinary editing. An online sequence of independent copies or the SQLite backup API alone cannot make uncoordinated vault writes and database state simultaneous: label such copies best-effort, verify them, and do not advertise point-in-time consistency. Never copy a live `.sqlite` alone. Test restore, then run recovery and filesystem reconciliation before serving writes. A files-only export is ordinary Markdown/attachments, not an identity-preserving backup: it recovers current bytes, paths, and reconstructible indexes, but not IDs, change cursors, revision DAG, tombstones, client acknowledgments, unresolved conflicts, historical blobs, or operation outcomes. If state is lost, assign new vault/entry IDs and a new random sync epoch; require clients to retain local data and reconcile/export manually rather than treating the empty history as authoritative. Never silently remap local edits by filename.

Restoring an older full backup is a history rollback: before accepting clients, generate a new sync epoch and cursor-signing key, invalidate snapshots and client acknowledgments, and force full reconciliation even though backed-up entry IDs are retained. Never reuse the old epoch, since a previously issued cursor could otherwise appear valid after sequence numbers are reused. The restore report identifies the backup time and warns that server-accepted operations and external edits after the backup may be absent; recover those from newer backups or client-held copies. Clients must treat the epoch change as potentially divergent history, preserving local dirty data and previously synchronized bytes pending explicit reconciliation. An internally consistent backup cannot recover changes that occurred after it was taken.

Paths in the wire API are vault-relative UTF-8, `/` separated, nonempty components, with no `.`, `..`, NUL, absolute path, backslash, control characters, or reserved server staging names. Enforce limits (default 4 KiB path, 255 bytes/component); reject invalid UTF-8 and report unrepresentable filesystem names to the administrator. Preserve spelling; compare using a per-vault portability key (Unicode NFC plus case folding) and reject collisions even on case-sensitive hosts, rather than silently changing names. Test host-specific normalization and case behavior; collisions discovered externally quarantine both entries from server writes and require manual repair. File extension `.md` is matched case-insensitively. Directory entries are implicit; empty folders are not synced in v1. Paths and IDs cannot cross vaults; cross-vault move is explicit export/import with a new ID.

Use directory file descriptors and descriptor-relative traversal (`openat`/`fstatat`, no-follow on every component), reject symlinks and special files, and check regular files, link counts and mount policy. Never resolve a user path with string concatenation alone. Reject traversal through symlinks including races; operate with least-privilege OS account and restrict root/state permissions. Platform-specific safe no-replace and rename primitives must be verified at startup; do not emulate no-replace with an existence check followed by rename. Vault and staging files for final replacement must be on the same filesystem; stage a hidden temporary file in the destination directory with exclusive creation, verify no traversal, then rename. Directory fsync is required where supported; unsupported durability semantics make the vault read-only, not silently weaker. Validate these assumptions on each supported platform/filesystem. Reject devices, FIFOs and symlinks and do not follow external links.

V1 platform target matrix: Linux on local ext4 or XFS and macOS on local APFS; container deployments use a bind mount or local volume backed by one of those supported Linux filesystems, not an overlay layer for vault data. These are **candidate targets**, not a claim that a particular kernel, mount option, storage controller or OS release has passed qualification. NFS, SMB, FUSE, network/distributed mounts and other filesystems are unsupported for writes. Linux uses `openat` with `O_NOFOLLOW|O_DIRECTORY` per directory, `fstatat(..., AT_SYMLINK_NOFOLLOW)`, `renameat2(..., RENAME_NOREPLACE)` for no-replace and `renameat` for validated replacement. macOS uses the equivalent descriptor-relative no-follow traversal, `renameatx_np(..., RENAME_EXCL)` for no-replace and `renameat` for replacement. Open regular staged files using `O_CREAT|O_EXCL|O_NOFOLLOW`, fsync file contents and fsync every affected directory after the rename; on macOS request `F_FULLFSYNC` for file content where supported. `flock` is used only for Andesite process ownership, never external-writer coordination. Check actual syscall results, support and mount type on the target volume; if directory fsync, required no-replace semantics or durability barriers cannot be obtained, refuse writes. Runtime probes establish syscall availability but cannot prove power-loss behavior: qualification also requires fault/power-loss testing on the deployment's OS/filesystem configuration. Do not silently fall back to check-then-rename. Use a per-vault startup capability report and read-only refusal on any failed mandatory probe.

## 5. Content, revisions and durable metadata

Represent exact bytes by lowercase SHA-256 plus length; do not normalize line endings, encoding, frontmatter or Markdown. Documents must be valid UTF-8 (BOM and CRLF preserved); invalid external `.md` is recorded as an opaque error, not rewritten. Attachments are arbitrary bytes. A revision is an opaque random ID, scoped to a vault entry, with parent revision(s), content hash, path, kind and tombstone flag. Revision IDs are never hashes alone: the same bytes can have different ancestry or path. Event sequence numbers are monotonically increasing 64-bit integers per vault and epoch, allocated in the same DB transaction as revision/outcome publication. Gaps are legal; ordering is commit order, not wall clock. Timestamps are informational.

Operational state is authoritative for identities, revision ancestry, previously captured contents, conflict proposals, event log, accepted idempotency outcomes, snapshot pins and tombstones. Derived state is headings, extracted metadata, links, backlinks, FTS and other parser outputs; rebuild from verified current files/revisions. Caches may be discarded freely. Missing/corrupt operational state cannot be reconstructed exactly from Markdown. Blob files are immutable, hashed on ingestion and durable before a DB row references them; garbage collect only after reachability checks and a grace period, with crash-safe mark-and-sweep. Old revisions and blobs remain as long as required by retention, unresolved conflicts, pending operations, active snapshots and idempotency records. Never GC an unresolved submitted version.

## 6. Mutation journal and recovery

The per-vault coordinator serializes Andesite's own mutations, observations and recovery; it cannot serialize external processes. Use SQLite WAL, foreign keys and `synchronous=FULL`. Durably write and fsync immutable objects and their parent directories before a database row references them. A submitted blob is *uploaded* but not an accepted operation until the durable outcome transaction commits. An accepted operation or captured revision remains recoverable within the retention and storage assumptions in §10.6. Bounded disk reserve, explicit errors and reachability-based GC apply to both Markdown and attachments.

### 6.1 Mutation state machine

For each request, serialize internally on the affected entry and namespace, and never await external work while holding a SQLite write transaction. The journal records client/operation ID and request digest, target entry, expected head and path, expected filesystem fingerprint, old and proposed content blobs, intended paths and revision, same-volume staging/recovery names, phase, and eventual outcome. The fingerprint is device/inode, regular-file type, size, change/modify timestamps and hash; it is evidence, not a filesystem CAS token. Record the phases and transitions durably; idempotent replays reuse the same operation ID. Directly before every destructive syscall, securely reopen and validate the path, type, inode/stat and content hash against the captured state. Match alone is not proof that no external write will race.

1. **Observe:** reconcile the relevant path and destination. Read a stable snapshot as in §7 and fsync its exact bytes as a preimage. If it differs from the database head, durably publish the external revision first, then compare the client's base again. A stable changed preimage never gets overwritten as if it were the old head. If a snapshot cannot be established, leave the request pending or return a retryable error without modifying the file.
2. **Prepare:** validate authorization, kind, UTF-8/size, destination and base; durable-store and verify the proposal and preimage blobs. Create an exclusive hidden same-directory staged file for a replacement or creation; fsync the file and directory. Commit a prepared journal record and idempotency reservation. No applied event or success has yet been published. If an external change is observed during staging, recapture it and turn the request into a durable conflict; do not apply it over that change.
3. **Revalidate and apply:** check source and destination immediately before mutation; on any detected discrepancy, stop before the syscall, capture the available external state, preserve the proposal and publish a conflict. Creation and a move destination use atomic no-replace rename; an existing validated target uses atomic replacement. A server delete renames to a unique same-filesystem recovery name rather than unlinking; a move uses no-replace rename. No platform primitive here conditionally checks source content: an external writer can still win the interval between validation and the syscall, or hold an open descriptor to a displaced file. Directory fsync follows successful filesystem changes. Do not recursively overwrite directories, follow symlinks or perform cross-device moves. Multi-entry directory moves are separate entry operations, not atomic.
4. **Verify:** immediately reopen the result and, for delete/move, inspect source, destination and recovery names. Capture stable unexpected bytes without replacing any path, including bytes readable from a retained descriptor or recovery name. A destination collision, unexpected content, path/type change, write-in-progress, or uncertain fsync leads to pending recovery or a durable conflict with all available evidence. If post-check observes the intended result, persist a verification marker containing the observed fingerprint and synced directory result; that marker proves only what the server observed, not that an external writer was excluded before or after it. Retain a displaced/recovery descriptor when practical, check it for later writes and retain the recovery file for a bounded grace period; this improves detection but cannot guarantee detection of future writes through other descriptors.
5. **Publish:** after the verified observation and durability barriers, commit in one SQLite transaction the revision/event, entry head, exact operation outcome, and journal completion. `applied` records the verified installation, not an enduring claim about present disk bytes. Return only after commit. Schedule immediate reconciliation: an external write after verification or commit becomes a later external revision when stably captured. If the mismatch is discovered before publication, do not claim `applied`; preserve the proposed version and observed disk version as a conflict or remain pending if evidence cannot yet be captured.

Before the durable outcome transaction, a client can poll `pending` and must retain its edit. If a confirmed external head conflicts with a submitted edit, use the existing `conflict_created` event and 409 conflict outcome; persist proposal and conflict atomically. Intent-only move/delete conflicts retain the requested action. A failure definitely before the filesystem syscall may durably return `not_applied`; repeating the same operation ID returns that same result, and a new attempt requires a new ID and refreshed base. If the syscall may have happened, do not claim `not_applied` merely because the old bytes are now visible: an external program may have restored them. Missing staging, unreadable evidence, failed fsync or an unresolved ambiguity leaves the operation pending and the affected entry/path blocked, not the entire vault unless shared storage or namespace integrity is compromised. Expose the incident via health and operation status; do not drop the staged proposal.

### 6.2 Restart and reconciliation

At startup take the server process lock, open the watcher, begin buffering hints, and recover prepared operations before accepting writes to their affected paths. External applications remain free to write throughout. Scan/revalidate current filesystem state while recovering; a watcher event is never proof of provenance. If the database already committed, return its stored outcome exactly; never repeat a committed syscall. For uncommitted prepares, do not infer that the server applied a change solely because current bytes match the proposed bytes: an external editor could have produced identical bytes or restored the old state. Even a persisted post-check marker is evidence of a prior observation, not proof of current disk state.

If a durable post-verification marker exists, captured evidence still agrees with it, and directory durability was confirmed, recovery may finish the recorded publication once; a subsequent scan captures later disk changes. Otherwise never blindly replay a destructive syscall. Capture every readable stable current/recovery version, retain proposal and preimage, and create an explicit recovery conflict with the actual observed state as head; if identity or absence cannot be established, keep the operation pending and isolate the entry. Resolve using the ordinary explicit conflict workflow after the filesystem has stabilized. `pending`, `conflict`, `applied`, and `not_applied` outcomes are persisted per operation ID and recovery is repeatable; SQLite's unique operation and event constraints prevent duplicate events. If a file changes during recovery, repeat observation or retain pending; never restore a DB blob over it. A committed head with changed or missing file becomes a later external revision/tombstone after a complete scan, not an automatic restore. A missing path observed during an ambiguous operation is not proof of deletion. A restart may finish startup for unaffected entries when the unresolved evidence is isolated; full-vault snapshot creation follows §10.2.

Disk-full or fsync failure before prepare fails without changing the target. After prepare or a syscall it leaves recoverable pending state, never a success. If the shared journal, DB or object store cannot durably record evidence, stop affected writes and, when shared integrity is at risk, make the vault read-only and alert. If underlying storage lies about durability or loses the journal/blobs, no software-only mechanism can uphold the durability claim.

## 7. External changes and indexing

Filesystem notifications are hints, not ordered or complete transaction records. Start watchers before the startup scan, buffer hints, process them after the scan, and repeat affected scans when changes overlap enumeration. Run periodic full reconciliation and a scan on overflow, watch loss or restart. A complete scan means all relevant directories were enumerated without permission/I/O errors and overlapping hints were revisited; even then it is not a simultaneous filesystem snapshot. On incomplete scans, never infer absence or tombstones for inaccessible subtrees; report diagnostics and retry. A deletion is recorded only after a successful parent/subtree enumeration and a later no-follow absence check; a recreation racing after that check is a later creation/revision when observed, not proof of a globally atomic scan.

Debounce events (default 250 ms, configurable) and retry changing files with bounded exponential backoff. For each candidate, securely open a regular file without following links; record descriptor identity/size/mtime/ctime, stream exact bytes while hashing into a private blob, re-stat the descriptor, then verify the path still points to the same regular file and re-read/hash if evidence changed or a new event arrived. Require two matching observations separated by the debounce interval before publishing, then fsync blob and directory and atomically commit the revision/event. Stable checks reduce, but cannot prove the absence of, an external write or detect every same-stat modification. A writer can pause mid-write long enough to look stable: capture such a snapshot if observed and publish a later one when it changes; never claim it is the editor's final save. If a file remains unstable or unreadable, postpone its publication and isolate that entry; do not overwrite or treat it as deleted.

A newly observed regular file becomes a new entry/revision. In-place writes and atomic-save replacement at the same existing path become an update to its existing ID after stable capture, unless rename evidence establishes a different identity. A verified external move retains ID only under §4's conservative evidence rules; ambiguous moves become delete plus create with new ID, preserving prior revision and exposing candidates. File-manager or shell batch renames are processed independently, never assumed atomic or inferred from hash alone. A confirmed disappearance publishes a tombstone retaining the prior revision. Attachments follow the same byte and identity rules. Ignore only Andesite's own reserved staging/recovery names, recognized by journaled name and identity; exclude the state directory. Do not globally ignore dotfiles or common editor temp suffixes: ordinary files, including temporary or partially written files, can be legitimate user data. Debounce and stable capture reduce noise, but may publish an external temp file before it is renamed or deleted; later observations generate ordinary events. Never delete a user temp file. Several rapid changes can collapse into one observed state; events need not capture every intermediate save.

Register an Andesite staging name and its expected file identity with the coordinator before processing watcher hints for it. A crash before durable registration can leave an orphan; recovery must not silently delete an unverified file merely because its name resembles server staging. Preserve it, report the orphan, and require identity/provenance evidence or explicit operator action before cleanup. Treat a journaled name replaced externally as unexpected user data, not as trusted staging.

External edits overlapping a client request are reconciled at pre-validation and post-validation; a detected head change causes the usual preserved conflict. A change between checks can be missed as explained in §1. If an external edit occurs after `applied`, it is an independent later revision; if the server's scan has not yet captured it, the filesystem remains canonical and the catalog is temporarily stale. Watcher overflow, unreliable event pairing, or notification loss triggers a full scan, not invented history.

If an externally edited `.md` is invalid UTF-8, capture its exact bytes as a durable incident blob, quarantine that entry from server writes and expose a diagnostic; do not publish the last valid revision as though it describes current disk content, nor emit a deletion. While unresolved quarantine, pending recovery, or an unreadable subtree makes a complete manifest uncertain, snapshot creation returns `vault_unreconciled` (503), but unrelated entry operations and existing change pulls may proceed. Entry reads for the affected ID return 503 rather than a stale head; incident bytes remain retained until explicitly resolved. Once corrected and stably captured, publish the external revision and clear quarantine. Unsafe names/collisions and incomplete scans follow the same conservative rule; no absence is inferred.

Index asynchronously from immutable revision blobs. Track `indexed_revision` per entry; discard stale parse results and retry. Search and backlinks may lag and return an index watermark/status; sync never relies on index freshness. An index rebuild creates new derived tables/FTS in a transaction or versioned shadow generation, then atomically switches readers; interruption leaves the previous generation usable. The catalog and operation tables are not dropped. Full scans use stat hints for scheduling but require periodic full hash audits because mtime/size alone are not proof.

## 8. Markdown and relationship semantics

Read bytes once, require valid UTF-8, retain them exactly. A frontmatter recognizer accepts a YAML block only at the start (after an optional BOM), bounded by delimiter lines `---` and a closing `---` or `...`; use a vetted safe YAML parser with size/depth/alias limits, no arbitrary object construction or network access. Invalid frontmatter is an extraction diagnostic and remains document text. Frontmatter is not rewritten. Store its parsed scalar/list/map projection separately; raw content is already in the file. Define a maximum frontmatter size (default 64 KiB).

Use swift-markdown's AST for CommonMark/GFM headings, text and ordinary links, with GFM fixtures for tables, task lists, autolinks and strikethrough; document unsupported variants instead of claiming all extensions. A separate source-aware extension lexer recognizes wiki links `[[target|label]]`, embeds `![[target#fragment|label]]`, and tags `#tag` in eligible text ranges only, excluding code blocks, inline code, HTML, escaped syntax, link destinations and frontmatter. Define backslash escapes and balanced delimiters; malformed constructs remain literal text. Heading outline preserves source order, level, text and source range; its fragment identifiers follow the exact v1 algorithm below. Tags use Unicode letters/numbers, `_`, `-` and `/` after `#`, with a word boundary; store display and case-folded keys. No parsing step serializes the AST back to Markdown.

**Heading slug v1** is an Andesite-defined algorithm, not a promise of identical behavior to GitHub or Obsidian. Use Unicode 15.1 normalization, case-fold and general-category data on all platforms, independent of the host OS's Unicode version. Traverse each heading's inline AST in source order: concatenate decoded text and inline-code literal text, recursively concatenate the visible children of emphasis, strong, strikethrough and link nodes, use image alt text, turn soft/hard line breaks into one U+0020, and omit inline HTML markup. Entity and Markdown escape decoding follows the parser. Normalize the resulting text to NFC, apply Unicode default full case folding (not locale-sensitive Turkic folding), and normalize to NFC again. For each scalar, emit `-` for each Unicode White_Space scalar; retain scalars whose Unicode general category begins `L`, `M` or `N`, and retain literal ASCII `_` and `-`; drop every other scalar. Do not trim, collapse hyphens, transliterate, or replace empty output. The result is the base slug.

Assign unique slugs in heading source order using a document-wide set. If the base has not been used, use it; otherwise try `base-1`, `base-2`, and so on and select the first unused value, including collisions with slugs produced by other base strings. Empty base is valid: the first empty slug is ``, the next is `-1`. Fragment matching percent-decodes UTF-8 once, without interpreting `+` as space, then compares the decoded fragment exactly to the assigned slug; do not case-fold the supplied fragment. Invalid percent encoding or UTF-8 is unresolved. An empty `#` is the document anchor, not an empty-heading reference. Fixtures, with each row a separate document unless grouped: `Hello, World!` → `hello-world`; ` A  B ` → `-a--b-`; `Café` and decomposed `Cafe\u0301` → `café`; `Straße` → `strasse`; `A_B / C` → `a_b--c`; `Hi 👋` → `hi-`; headings `Foo`, `Foo`, `Foo-1`, `Foo` → `foo`, `foo-1`, `foo-1-1`, `foo-2`; headings `!!!`, `???` → ``, `-1`. Store slug algorithm/version in the index generation; changing it requires rebuild and an API-visible version change.

**Extension lexer v1:** operate on original UTF-8 source ranges marked as eligible plain text by the CommonMark parser, without crossing range or line boundaries; spans are half-open UTF-8 byte offsets. Within each range scan left to right. An odd run of backslashes immediately before `[` or `#` escapes that character; an even run does not. At `![[` or `[[`, take the first unescaped `]]` on the same line; nested unescaped `[[` makes the whole candidate literal. Split the interior at the first unescaped `|`, then split the target at its first unescaped `#`; remove backslash escapes only for `\\`, `[`, `]`, `|`, and `#`. Target must be nonempty after trimming ASCII spaces/tabs, except `[[#fragment]]` is a same-document reference; fragment and label, if present, must be nonempty after the same trim. Invalid syntax stays literal; an embed is the same occurrence with kind `embed` and includes the leading `!` in its span. Occurrences inside one recognized construct are not rescanned for tags or links. A tag begins at an unescaped `#` only when preceded by start of eligible range or a scalar that is not a Unicode letter, number, mark or `_`; consume one or more Unicode letters/numbers or `_`, `-`, `/` and stop at the first other scalar. A bare `#` is not a tag. Wiki links resolve using the target and fragment after unescaping, not display text. Keep raw source unchanged.

Lexer conformance examples (each shown as raw Markdown; outcomes omit byte offsets): `[[Note]]` → wiki target `Note`; `![[Note#Part|shown]]` → embed target `Note`, fragment `Part`, label `shown`; `[[#Part]]` → same-document wiki fragment `Part`; `[[A\|B|C]]` → target `A|B`, label `C`; `\[[No]]` → no occurrence; `[[A [[B]]` → no occurrence; `` `[[No]] #no` `` and fenced code containing `[[No]]` → no occurrences; `[x](notes/#no)` → no tag; `#work/project` → tag `work/project`; `word#tag` → no tag; `#` → no tag; `[[A|]]` → no occurrence. AST implementation must preserve sufficient eligible source ranges to implement these examples; if it cannot, use a source-aware tokenizer rather than interpreting unavailable ranges as safe text.

Extraction yields raw link occurrences, spans, kind, target, label and fragment, plus headings/tags/metadata. Resolution is separate and deterministic: external URI schemes are not vault links; relative standard Markdown targets resolve from the source directory after percent-decoding once and safe path normalization; `#fragment` targets the current document. Wiki path targets resolve relative to source first, then from vault root; bare names resolve by exact normalized basename among Markdown files, with `.md` optional. A unique match resolves; multiple matches are **ambiguous**, never arbitrarily chosen. Reference-style Markdown links use the AST's resolved destination. Binary targets are attachments; embed is a relationship flag, not an instruction to execute/render content. Missing paths and heading fragments remain unresolved with reason. Standard Markdown links do not receive wiki fallback.

Maintain reverse lookup keys for path, basename and fragment dependencies. When a file's path, name, headings or existence changes, invalidate the union of sources referencing old and new keys, plus links originating in that document. Re-resolve affected sources transactionally and update backlinks. Never auto-rewrite user text on rename; previously spelled references may become broken/ambiguous. Full rebuild is the correctness oracle for incremental indexing. Parser dialect and resolver versions are stored with index generations.

## 9. SQLite design

Types: UUIDs as 16-byte blobs, hashes as 32-byte blobs, sequence as INTEGER, timestamps UTC; JSON denotes bounded validated JSON text. Primary keys are explicit. Enforce foreign keys, unique path portability keys and constraints. Core schema (columns shown are minimum; all vault-scoped keys include vault_id):

* `vaults(id PK, root_config, epoch, next_seq, min_seq, created_at, state)`.
* `entries(vault_id, id, kind, path NULL, path_key NULL, head_revision NULL, state, fs_hint, PRIMARY KEY(vault_id,id))`; state is `reserved`, `live`, `deleted`, or `retired`. Use a partial unique index `(vault_id,path_key) WHERE state='live'`. Reserved IDs support create conflicts without a live path or head.
* `revisions(vault_id, entry_id, revision_id, parent1 NULL, parent2 NULL, content_hash NULL, byte_length, path, deleted, origin, created_at, PK(vault_id,revision_id))`; parent2 is reserved for explicit conflict resolution. Parent IDs remain as historical identifiers even if older revision rows are pruned, rather than enforcing a foreign key that prevents retention cleanup. Tombstones retain prior content through parent history while that history is retained.
* `objects(hash PK, length, durable_location, created_at)`; shared immutable blob metadata, with reachability checked before deletion.
* `changes(vault_id, seq, entry_id, revision_id NULL, conflict_id NULL, type, operation_id NULL, payload_json, PK(vault_id,seq))`; index `(vault_id,entry_id,seq)` and unique operation/event associations as appropriate. Immutable payload retains the facts as of the event, including conflict intents.
* `tombstones(vault_id,entry_id,revision_id,seq,deleted_at, PK(vault_id,entry_id))`.
* `clients(vault_id,client_id, acknowledged_seq, epoch, last_seen, PK(vault_id,client_id))`; acknowledgments are retention hints, never authorization or a substitute for the client's durable local cursor.
* `operations(vault_id,client_id,operation_id,request_hash,state,outcome_json,created_at, PK(vault_id,client_id,operation_id))`; persist accepted and deterministic conflict outcomes. `pending_operations` additionally stores the durable prepare and phase, pre/post hashes, paths, staging and object references. Unique operation IDs are never reused for different payloads, even after success.
* `conflicts(vault_id, conflict_id, entry_id, operation_id, intent_type, requested_path NULL, base_revision NULL, observed_head NULL, submitted_revision NULL, status, created_at, resolution_revision NULL)`; store intent details and resolution audit. Submitted revisions and bytes remain reachable until resolved and retention conditions permit deletion.
* `snapshots(vault_id,snapshot_id,epoch,high_seq,expiry,state)`, `snapshot_items(snapshot_id,entry_id,revision_id,path, PK(snapshot_id,entry_id))`, and `snapshot_conflicts(snapshot_id,conflict_id,frozen_payload_json, PK(snapshot_id,conflict_id))` pin a point-in-time manifest, conflicts and referenced revisions/objects.
* `vault_objects(vault_id,hash,reference_kind,reference_id)` and `blob_leases(vault_id,principal_id,hash,expiry)` authorize vault-scoped downloads and pin uploaded objects; incident records pin quarantined external bytes. An ID graveyard preserves retired entry IDs after detailed tombstones are compacted.
* Rebuildable `document_metadata(vault_id,entry_id,indexed_revision,title,frontmatter_json,outline_json,...)`, `tags(vault_id,entry_id,tag_key,...)`, `link_occurrences(vault_id,source_id,ordinal,raw_target,lookup_key,fragment,kind,status,target_id NULL,...)`; indexes on `(vault_id,target_id)` and `(vault_id,lookup_key)` for backlinks and invalidation. `attachment_metadata(vault_id,entry_id,revision_id,size,content_hash,media_type)` is derived from verified entry/revision metadata; media type is advisory. FTS5 virtual table contains entry ID, title and extracted text; scope queries by vault with a mapping table, tokenize using `unicode61`; never interpolate raw search syntax without defining query semantics and bounds.

Migrations are numbered, transactional where SQLite permits, run exclusively after backup, check `user_version`, and refuse newer unsupported schemas. WAL gives concurrent readers with one writer, not multiple simultaneous writers; keep read transactions short to avoid WAL growth, checkpoint with monitoring, bound busy timeouts and retries. SQLite's backup API includes a consistent database view, but does not by itself make external files/blobs consistent. Limit write transaction duration; never await network or parse Markdown while holding one.

## 10. Sync protocol v1

### 10.1 General wire rules

HTTPS JSON control plane under `/v1`, raw byte streams for blobs. All IDs are lowercase UUID strings, SHA-256 values 64 lowercase hex characters, sizes and sequence numbers nonnegative decimal **strings** to avoid JavaScript precision loss. Timestamps are RFC 3339 UTC. JSON is UTF-8; unknown optional response fields must be ignored. Requests reject unknown operation types; all limits and errors are explicit. Authentication and authorization apply to every vault, snapshot, blob and operation request; a hash is not authorization. IDs and cursors are opaque to clients. Responses are `Cache-Control: no-store` for sensitive metadata, and blob reads verify digest.

A cursor is an opaque authenticated token containing version, vault ID, epoch and last sequence. It cannot be moved between vaults/epochs. It means **all events through that sequence were durably applied by the client**, not merely received. Server issues a next cursor after a page; client persists page effects and cursor atomically in its local store. On crash it repeats the same page. Client acknowledgment is sent only after local commit; retries are harmless. `min_seq` defines earliest retained event, and cursor `s` is valid iff `s >= min_seq - 1` and `s <= current_seq`. No stable guarantee follows from wall-clock time or presence of a client record.

Cursor encoding v1 is unpadded base64url of exactly 77 bytes: version byte `01`, 4-byte unsigned key ID in network byte order, 16 RFC 4122 UUID bytes for vault, 16 UUID bytes for epoch, 8-byte unsigned big-endian last sequence (limited to SQLite signed 64-bit maximum), and 32-byte HMAC-SHA256. The MAC input is the ASCII domain separator `andesite.cursor.v1` followed by a zero byte and the first 45 bytes of the token. Generate keys using a cryptographically secure RNG, at least 32 bytes each, store encrypted or OS-permission-protected with the state directory and include them in full backups. Reject malformed, noncanonical base64url, wrong length, unsupported version, unknown key ID or bad MAC without interpreting unauthenticated fields; compare tags in constant time. Check authorization independently after verification. Key IDs are never reused. To rotate, atomically install a new active key and issue all new cursors with it; retain old verification keys indefinitely for uninterrupted cursor validity, since a cursor in a quiet vault need not expire merely with passage of time. Administrators may deliberately revoke an old key after communicating that affected clients must reconcile; forced revocation or loss of an old key returns `cursor_invalid` (410) and requires full reconciliation. Never accept a partially decoded cursor. Restore of an older backup rotates epoch as specified in §4. Never log cursor keys or tokens.

### 10.2 Initial and full reconciliation

`POST /v1/vaults/{vault}/snapshots` creates a durable snapshot manifest in one short SQLite transaction at high-water sequence H, including every live entry's ID, path, type, head revision, hash and size; pin referenced objects. Before creation the coordinator reconciles queued observations and checks that there is no unresolved operation, quarantined entry or incomplete scan that makes the manifest unsafe; otherwise return 503 `vault_unreconciled` without blocking unrelated entry operations. The manifest is a consistent projection of the **published catalog** at H, not an atomic snapshot of mutable vault files: unobserved or not-yet-captured external changes can make it temporarily stale. Changes captured later receive sequences after H; changes overwritten before observation may never become events. Snapshot creation can return 202 with a status URL for large vaults. Paginate deterministic ID-sorted frozen items: `GET .../snapshots/{snapshot}/entries?limit=...&page=...`. Manifest pages and blobs are immutable, even as heads change. A snapshot has a default 24-hour TTL; expiry returns `snapshot_expired`, requiring a new snapshot. Release explicitly or on expiry. No tombstones are needed in a manifest because it is a complete enumeration of the published catalog; never infer absence from incomplete pages.

Client fetches/verifies required blobs, stages the full manifest locally and atomically reconciles it without discarding local edits or pending operations; then persists the snapshot's opaque cursor for H. It replays `changes?cursor=<snapshot-cursor>` for changes committed during enumeration. If H has expired by then, create another snapshot and repeat while retaining local edits; the server MUST pin the event floor needed by a live snapshot until snapshot TTL expires. For a fresh cache install, applying manifest is straightforward. For a disconnected existing client with expired history or a new epoch, compare old locally known base, local dirty bytes and new server state by stable IDs only within the same epoch. Preserve dirty data and pending operations as local conflicts/exports; IDs from a changed epoch are not implicitly related. If base history is unavailable, require explicit user decision or save as a new path; do not assume equal paths imply identity. An absent server ID may mean deletion, not permission to erase dirty local content.

The snapshot also freezes the IDs and immutable details of all unresolved conflicts at H, exposed through `GET .../snapshots/{snapshot}/conflicts` with the same pagination and expiry rules as entries. Its pins include conflict proposals and any retained base revisions. Client reconciliation stages both complete enumerations before advancing to H; later conflict changes arrive in the event stream. This prevents full reconciliation from losing visibility of an old unresolved conflict after its creation event expires.

### 10.3 Incremental pull

`GET /v1/vaults/{vault}/changes?cursor={token}&limit=200` returns ordered events and `nextCursor`, `hasMore`, and `highWater`. Each event contains sequence, entry ID, revision ID, type (`created`, `updated`, `moved`, `deleted`, `restored`, `conflict_created`, `conflict_resolved`), path, content hash/size when applicable, and origin operation ID if applicable. Each revision event references an immutable blob; fetch by hash or `GET .../entries/{id}/revisions/{revision}/content`. A page stops at a stable H captured for that request. Events remain accessible during the configured retention interval, but a client must handle expiration between pages. Fetch revision blobs before committing a cursor if needed to reconstruct cache; repeated revisions may be coalesced only if doing so preserves local dirty state and conflict events. `cursor_expired` (410) and `epoch_mismatch` (409) require full reconciliation. Changes to an entry can be repeated; use revision/sequence identity to apply idempotently. Optional SSE/WebSocket notification contains only a hint to pull; missed or reordered hints do not affect correctness.

### 10.4 Blob transfer

`PUT /v1/vaults/{vault}/blobs/{sha256}` streams exact bytes with `Content-Length`, `Content-Type: application/octet-stream`; enforce configured maximum (defaults 10 MiB Markdown, 1 GiB attachments) before and during transfer. Server hashes and fsyncs a temporary object before atomically publishing it; mismatch is 422, no operation submitted. Repeat PUT is idempotent. `GET` streams a retained, vault-authorized referenced blob with length and digest; range reads may be added but v1 clients can retry whole uploads/downloads. Unreferenced uploaded blobs are leased to the authenticated uploader for 24 hours, then GC eligible; an operation must refer to an uploaded retained blob accessible to its principal. Prevent cross-vault hash existence leaks. A client MUST retain its own edit until the operation outcome is durable and acknowledged locally.

### 10.5 Submit and conflict behavior

`POST /v1/vaults/{vault}/operations` submits **one** operation per request, independent atomic outcomes; no batch atomicity. Body fields: `clientId`, `operationId`, `type`, `entryId`, `baseRevision` (null for create and for resolution of an uncreated reserved ID), `path` where applicable, `contentHash` and `size` where content applies. Types are `create`, `update`, `move`, `delete`, `restore`, `resolve`. Create uses a client-generated entry UUID; the server rejects an ID already used, including tombstones, without claiming to retain the proposal. Other mutations require a base revision except the specified resolution case, and every resulting live path must pass uniqueness checks. `move` changes only path; combined content+move requires separate operations. Restore requires a tombstone head and retained uploaded content. Clients serialize dependent operations per entry, but operations on different entries may be parallel.

Idempotency scope is `(vault, clientId, operationId)`. Compute a canonical semantic request hash over normalized fields; while the record is retained, same key and same hash returns the exact durable original result, including conflict, regardless of later head changes. Same key with a different hash returns 409 `idempotency_key_reused`. Concurrent duplicates join or observe the prepared operation. `GET /v1/vaults/{vault}/operations/{clientId}/{operationId}` returns `pending`, committed result, or `not_found`; `not_found` is not evidence that a previous expired record was never applied. Persist idempotency records at least 90 days; after this period, clients must not blindly retry an uncertain old operation or ever reuse its ID: reconcile first and use explicit conflict resolution/new operation ID. The server cannot detect reuse once its record has expired. Advertise the actual expiry in outcomes. Preserve outstanding recovery records regardless of age.

If `baseRevision == current head` and destination is safe, attempt the journaled mutation; equality is necessary, not a guarantee against unobserved external changes. Otherwise, for an update/restore whose submitted bytes are present, retain the submitted blob and create a durable conflict proposal based on the supplied base, **without changing the canonical head**. Return 409 `revision_conflict` with `conflictId`, submitted revision, current head and their metadata. A move/delete with a stale base records a conflict intent and leaves the head unchanged; its intended path or deletion is preserved. A path collision yields 409 `path_conflict`, with the proposal retained for content-bearing operations, including create; for create the proposal records the reserved entry ID without publishing a live entry. A move collision retains the intended path as a conflict intent. No server-side automatic merge or winner selection occurs. Unknown or pruned base still yields a preserved proposal if the entry identity and bytes are valid; identify `base_unavailable`. A nonexistent/invalid entry or malformed request is rejected without claiming retention, and the client keeps its copy. An external or recovery ambiguity detected during mutation uses the same `conflictOutcome` and conflict event, with `error.code` `filesystem_conflict` or `recovery_conflict`; if its current state cannot yet be durably captured, return or retain `pending` instead. Reconcile the current file again immediately before a `resolve`, including `keep_head`, so a newly observed external head is not dismissed as stale catalog data.

Example: devices A and B both edit revision R while offline. A submits A1 first; it becomes head A1. B submits B1 based on R; B1 is durably retained as a conflict and A1 stays on disk. Pull exposes conflict to authorized clients. A user reads R (if retained), A1 and B1 and submits chosen or manually merged bytes as `resolve`, naming the conflict and current head as base. If head has moved again, resolution itself conflicts and all versions remain. On success the new revision references current head and proposal as parents, marks that conflict resolved, emits `conflict_resolved`, and retains both ancestors subject to retention. A delete versus edit is handled identically: a stale deletion never removes the newer edit; an edit against a tombstone becomes a preserved proposal, not an implicit resurrection. An external update observed between device edits is a head revision and causes the same comparison.

#### Operation field and resolution contract

Every request includes `clientId`, `operationId`, `type`, `entryId` and `baseRevision`. All unspecified fields are rejected for that type. `kind` is `markdown` or `attachment`; entry kind is immutable. A blob's declared size must match its stored length. A Markdown path must have the `.md` extension and Markdown bytes must be UTF-8; attachments may not use `.md`.

The extension rule also applies to destinations of moves, restores and resolutions. A path already owned by the same live entry is allowed; a path owned by a different entry is a collision. If a supplied base revision exists, it must belong to the named vault and entry; a revision of another entry is invalid rather than a merge parent. An unknown base is handled as `base_unavailable` without inventing a parent revision. The request hash uses a canonical length-prefixed encoding of the operation type and its validated typed fields in the order in the table, including explicit nulls; it hashes decoded values, not JSON serialization, so object member order cannot change idempotency.

| Type | Additional required fields | Effect when preconditions hold |
|---|---|---|
| `create` | `kind`, `path`, `contentHash`, `size`; null base | Reserve unused entry ID and create a live head. |
| `update` | `contentHash`, `size` | Replace bytes at current path; head must be live. |
| `move` | `path` | Change live entry path only. |
| `delete` | none | Tombstone the live head. |
| `restore` | `path`, `contentHash`, `size` | Restore a tombstoned entry at an available path. |
| `resolve` | `conflictId`, `resolution` | Resolve exactly one open conflict against the current head, or against null for an uncreated reserved ID. |

`resolution` is an object with `action`: `write` requires `path`, `contentHash`, `size`; `delete` has no additional fields and creates a tombstone; `keep_head` has no additional fields and explicitly dismisses the proposal. `write` may select either version or uploaded merged bytes and requires a free path; for a live entry the path must equal its current path, so moving it requires a subsequent separate `move`. A tombstoned or uncreated entry may use any free path. For an existing entry its revision parents are the current head and the submitted content revision when one exists. For a move/delete intent there may be no content proposal parent; retain the intent in the audit record. `keep_head` makes no filesystem change but emits `conflict_resolved` referencing the unchanged head. For an uncreated ID, `write` creates its first head, while `delete` or `keep_head` closes the proposal and permanently retires the reserved ID without creating a file. Resolution of an already resolved conflict fails with `conflict_closed`; a stale resolution preserves any newly uploaded `write` proposal as another conflict, leaving the original unresolved. A `resolve` with null base is valid only for an uncreated reserved ID, an exception to the general base rule.

Each conflict record has its own UUID, entry ID, original operation ID, intent type, base revision if supplied, observed head if any, requested path if any, submitted revision/hash/size if any, status, and timestamps. Conflict creation and its sequence are committed atomically with the original operation outcome. A `conflict_created` event includes `conflictId` and the observed head (which may be null); a `conflict_resolved` event includes `conflictId`, action, and resulting head (which may be null). Such events need not contain content bytes; the conflict detail and referenced blob endpoints provide them. Event types for regular revisions always include revision, path and, for live revisions, hash and size. A delete includes the tombstone revision and last path with null hash and size. The changes table must therefore store conflict ID and a durable immutable event payload, not just a revision foreign key.

Snapshot creation returns `snapshotId`, `expiresAt`, `epoch` and the opaque `cursor` at H; an asynchronous 202 returns a status URL that eventually provides the same fields. Each entries or conflicts page returns `items` and `nextPage` (null when complete); tokens are opaque, bound to snapshot and enumeration type. `DELETE .../snapshots/{snapshot}` releases pins and returns 204. `POST /v1/vaults/{vault}/clients/{clientId}/ack` takes `{"cursor":"..."}` and returns 204 after monotonically recording a valid same-epoch acknowledgment; stale acknowledgments are no-ops. An acknowledgment does not advance the client's own cursor and never permits the server to delete required history before its retention deadline.

`GET .../conflicts/{conflictId}` returns the complete record and per-revision metadata, with nulls for unavailable pruned bases; a missing historical blob returns 410 `revision_expired`, while a missing blob that is still pinned returns 503 `storage_corrupt`. A client may fetch its conflict proposal even if its creation event has expired. Blob downloads are authorized through vault-scoped retained revision or active uploader lease; the server maintains vault/object references and principal leases in SQLite so global hash deduplication cannot confer access.

### 10.6 Retention and recovery

Default retain change events and historical revisions/blobs for 90 days; resolved conflicts retain their revisions for at least that period, unresolved ones indefinitely. The admin may set longer but not lower than the advertised minimum without an explicit maintenance procedure. Client acknowledgments inform GC but do not block it forever. Every retained event pins the revision and blob required to replay it, even when that revision predates the event. Never GC a blob pinned by a retained event, live snapshot, operation, unresolved conflict, current head or retention policy. Advance the event floor transactionally only after checking pins; an expired cursor gets 410, not a partial stream presented as complete. Tombstones survive at least as long as events and their entry IDs are never reused within an epoch; compact detailed tombstones to an ID graveyard when safe. Retention expiration does not delete current vault content. Regular integrity checks detect missing referenced blobs; affected sync/history requests fail with an explicit corruption error instead of fabricated data.

### 10.7 Wire examples, schemas and errors

The normative JSON Schema 2020-12 document is [`andesite-protocol-v1.schema.json`](andesite-protocol-v1.schema.json). Select the indicated `#/$defs/` member for each message; schema validation supplements, rather than replaces, the semantic, authorization, path, size, revision and hash checks in this specification. Response objects allow unknown extension fields; operation and acknowledgment request objects reject unknown fields. `format: date-time` is mandatory, not merely annotation. Decimal strings must additionally be at most 9223372036854775807. Page limits default to 200 and are integers from 1 through 500; invalid limits return 400 rather than being silently clamped.

`capabilities.externalWriterLockRequired` is always `false` in this revised v1. The earlier draft's `true` value contradicted filesystem-first operation; changing the constant is necessary to state the corrected contract, not a new coordination mechanism. No operation types are added. The optional `conflict.evidence` array supplies `{contentHash, size, role}` for retained preimage, observed or recovery bytes when those are not otherwise discoverable from the conflict's head/proposal. This backward-compatible response field permits authorized clients to inspect ambiguous filesystem evidence using the existing blob endpoint; each listed object is vault-authorized and pinned through conflict retention, included in frozen snapshot-conflict details, and subject to the same access checks as other conflict content. When evidence is not yet safely captured, the operation remains pending rather than publishing a misleading incomplete conflict. `applied` and the existing `pending`/`conflict` outcomes have the meanings in §6; an authenticated client must not assume `applied` makes the filesystem immutable against subsequent external writers.

| Endpoint | Request / success response schema |
|---|---|
| `GET /v1/capabilities` | no body / `capabilities` |
| `GET /v1/vaults` | no body / `vaultPage` |
| `POST .../snapshots` | empty body / `snapshot` (200 or 201), or `snapshotPending` (202) |
| `GET .../snapshots/{id}/entries` | no body / `entryPage` |
| `GET .../snapshots/{id}/conflicts` | no body / `conflictPage` |
| `GET .../changes` | no body / `changesPage` |
| `POST .../operations` | `operationRequest` / `operationOutcome` (200 applied, 202 pending, 409 retained conflict, or persisted `not_applied` error) |
| `GET .../operations/{clientId}/{operationId}` | no body / `operationOutcome`; 404 if unknown or no longer retained |
| `POST .../clients/{clientId}/ack` | `ackRequest` / 204 empty body |
| `GET .../entries/{id}` | no body / `entry` for a live, reconciled head; tombstoned entries return 410, quarantined heads return 503 |
| `GET .../conflicts` and `GET .../conflicts/{id}` | no body / `conflictPage` and `conflict` respectively |
| `GET .../search` and `GET .../backlinks/{id}` | no body / `searchPage` and `backlinkPage` respectively |
| `GET /v1/health` | no body / `health` |
| `DELETE .../snapshots/{id}` | no body / 204 empty body |

Other error responses use `errorResponse`, except a retained conflict uses `conflictOutcome`. Operation status includes the same original result and HTTP status as submission, except pending uses 202. For asynchronous snapshot creation, `statusUrl` returns `snapshotPending` with 202 until it returns `snapshot` with 200 or a standard error. For all paginated endpoints `nextPage` is an opaque token accepted as the `page` query parameter, scoped to the authenticated principal, endpoint and vault; expired or invalid tokens return 410 `page_expired` and callers restart that enumeration. Search/backlink pages are eventually consistent and may change between enumerations; snapshot pages alone are frozen.

Do not retry validation failures unchanged. Cancellation after prepare leaves a queryable operation.

## 11. API surface, access and operations

Minimal additional endpoints: `GET /v1/capabilities` (protocol versions, limits, retention, features), `GET /v1/vaults`, `GET /v1/vaults/{vault}/entries/{id}` (head), `GET /v1/vaults/{vault}/conflicts` and conflict detail, `GET /v1/vaults/{vault}/search?q=...` (bounded FTS query and index watermark), `GET .../backlinks/{id}`, and authenticated `/v1/health` (recovery, indexing and lock errors). All listing/search endpoints paginate with bounded limits. Explicit JSON schemas/OpenAPI and language-neutral conformance vectors are release artifacts; examples above do not replace them. Administrative vault provisioning, backup and restoration are local CLI/configuration in v1, not remotely exposed.

Default bind loopback; require TLS for non-loopback use, either configured server TLS or a trusted local reverse proxy with TLS. Do not trust forwarded identity/headers from arbitrary clients. Provision high-entropy bearer tokens out of band; store only secure token hashes, compare safely, rotate/revoke, and grant per-vault read/write scopes. Never log tokens or document contents. A browser client uses `Authorization` headers, exact configured CORS origins and no wildcard credentials; no cookie auth in v1, avoiding ambient-cookie CSRF. CORS is not authorization. Enforce request/body size, connection, rate and time limits; expose audit events for authorization failures and mutations without contents. Prevent Markdown rendering of scripts in clients; backend never executes embeds or fetches remote links.

Structured logs include request/operation/vault IDs, durations and error codes, not content or sensitive paths by default. Metrics: pending journal age, recovery incidents, scan/watch overflow, index lag, event floor, WAL size, blob/DB disk usage, FTS failures, conflicts and request latency. Graceful shutdown stops admission, completes or leaves prepared operations recoverable, flushes and closes connections. Readiness stays false until startup has classified recovery records, established affected-entry blocks and attempted the initial scan; it may then report degraded while isolated incidents remain. Snapshot creation remains unavailable if its completeness is uncertain. Liveness must not imply storage health. Disk-full, corrupt DB, missing objects and process-lock failure cause explicit degraded/read-only behavior as scoped by the failure and operator alerts. Use SQLite integrity checks, object hash audits and tested backups; encryption at rest is a deployment responsibility.

## 12. Verification and delivery gates

1. **Foundation:** pin dependencies, compile in Swift 6 strict mode on supported Linux/macOS and container; test FTS5/WAL, locking, safe no-replace, fsync and path protections on each target filesystem. Refuse unsupported configurations.
2. **Storage and recovery:** use a fault-injection harness to crash at each journal boundary, including staging/fsync, prepare, rename, directory fsync, DB commit and cleanup; restart repeatedly. Verify retained accepted proposals/preimages remain available, no event precedes durable content, detected unexpected external files are not overwritten, and disk-full/permission errors produce recoverable state. Test no-replace races, symlink swaps, case collisions, Unicode, hard links, ENOENT and cross-device rejection. Explicitly demonstrate the external-writer race rather than misrepresenting it as solved.
3. **Markdown/index:** golden tests for byte preservation, malformed YAML, AST exclusions, wiki ambiguity, fragments, links and external renames; compare incremental graph/FTS results with clean rebuild. Exercise watch overflow and incomplete scans.
4. **Sync:** implementation-independent fixtures for two offline edits, delete/edit, move/edit, repeated operation after lost response, concurrent duplicate IDs, stale bases, snapshot changes between pages, retention expiration, restart, missing blob, interrupted transfer, epoch loss and full reconciliation. Assert local dirty data and every accepted proposal remain recoverable; apply pages twice to test idempotence. Fuzz bounded JSON, paths and cursors.
5. **Operations:** backup/restore drills with quiesced or storage-snapshotted vault and state, including files-only recovery and new epoch; verify client reconciliation, SQLite corruption alarms and object reachability. Load test large vaults, slow disks, bounded memory and watcher backlog before selecting operational limits.

### Required scenario review and conformance cases

The following are design expectations, not claims that fault-injection tests have already been run. In all cases captured/accepted blobs survive within §10.6 retention and the stated disk-durability assumptions; uncaptured external writes have no such guarantee.

| Scenario | Observable behavior and durability | Residual risk and recovery |
|---|---|---|
| 1. VS Code edits a file online | Watch hint or scan leads to stable capture and an external update event; filesystem remains canonical and old retained revisions remain available. | Editor may save again between observations; intermediate writes are not guaranteed. Retry unstable reads and reconcile the final observable state. |
| 2. Client update overlaps an editor | A changed precheck or postcheck yields a durable conflict preserving submitted and captured versions, or `pending` until capture succeeds. | A write in the validation/rename gap may be overwritten undetected; an edit after verified installation becomes a later event if observed. Client retains bytes until outcome and user resolves detected conflicts. |
| 3. Editor uses temp-file replacement | Debounce and capture resulting path as an update with existing ID; external temp files are not deleted and may briefly appear as entries. | A short-lived temp or intermediate state can be missed; repeated reconciliation captures the eventual stable file, not a guaranteed edit history. |
| 4. Script rapidly renames documents | Paired evidence plus validation can preserve IDs; otherwise emit conservative tombstone/create pairs with old revisions retained. | Hints may be coalesced or ambiguous; never guess ID from equal hash. Surface candidates for explicit relink and allow offline clients to reconcile. |
| 5. Watcher loses events | Overflow or periodic scan discovers persistent differences and emits ordinary revisions; incomplete scans do not manufacture deletions. | Transient edits lost before scanning are unrecoverable; reestablish watcher and perform full hash reconciliation. |
| 6. Crash after filesystem syscall, before DB publication | Durable prepare and blobs remain; operation remains pending on restart. A durable verified marker plus matching evidence may finish publication once; otherwise capture current state and produce recovery conflict or remain pending. | Matching bytes alone cannot prove who wrote them. No blind replay or false success; operator/client resolves preserved proposal and evidence. |
| 7. External file changes after final check, before replacement | Server may replace the external write despite checks; preimage and submitted proposal remain retained. If discrepancy is observed, stop and create conflict or pending recovery. | Counterexample: external write finishes entirely in the gap and its inode is replaced; neither hash nor watcher necessarily yields its bytes. Only a separately captured copy or backup can recover it. |
| 8. Writer continues through an old open descriptor | Server retains and rechecks a displaced descriptor or recovery file where possible; any stable readable unexpected bytes are captured as evidence. | Counterexample: writer writes after the last check to an unlinked old inode, then closes it; the change can be unreachable and invisible. Best-effort monitoring cannot guarantee recovery. |
| 9. Two offline clients edit R | First accepted change becomes a verified revision; second stale submission is retained as a conflict, and no automatic merge or discard occurs. | An independent external write can also race as in cases 2 and 7. Clients fetch head/proposal and explicitly resolve with a current base. |
| 10. Restart with pending operations and external edits | Recovery observes rather than overwrites current files, pins all available blobs, and blocks only affected entries while pending; other entries may serve. Confirmed conflicts appear through normal sync. | Files can keep changing throughout recovery; never infer provenance from matching hashes. Retry stable capture or require manual recovery, preserving proposals and evidence. |

Open implementation gates: power-loss qualification of the candidate filesystem/OS matrix; audited Swift YAML dependency and parser fixtures; tested pinned SwiftPM versions; operator CLI/config syntax; automated JSON Schema and protocol-conformance validation. These are prerequisites for release, not permission to weaken the guarantees above.

### Design review trace

The specification was reviewed against the requested failure and portability cases: identity and uncertain external renames (§4); full versus files-only backups and restore epoch rollback (§4); watcher loss, incomplete scans and external revisions (§7); snapshot, cursor, offline conflict and retention rules (§10); and prepare, filesystem mutation, publication, disk-full and crash recovery (§6). The JSON Schema was meta-validated with a Draft 2020-12 validator, and representative valid requests for all six operation types, a rejected unknown request field, snapshots, entry pages, each event type, conflict outcome, acknowledgment and errors were checked against it. This is a design/schema check, not a test of a server implementation, actual crash behavior, all semantic constraints or Linux/macOS filesystem durability. Automated cross-platform and full protocol conformance testing remains required before release.
